# 10.4 CUSTOM BUSINESS LOGIC (HOOKS SYSTEM) — IMPLEMENTATION PLAN

---

# 1. PURPOSE

The Hooks System enables execution of **custom business logic in response to system events**.

It allows:

* Tenants to define automated behaviors
* Modules to extend system functionality
* Developers to inject logic without modifying core code

---

# 2. GOALS

### Primary Goals

* Event-driven architecture
* Support dynamic and static entities
* Allow safe execution of custom logic
* Enable both system-level and tenant-level hooks

### Non-Goals

* No arbitrary unsafe code execution
* No direct database manipulation bypassing APIs
* No blocking critical system operations (must be controlled)

---

# 3. CORE CONCEPT

Hooks are **functions triggered by events**.

### Example

> When a Loan is created → calculate repayment schedule

---

## 3.1 Hook Lifecycle

```text
Event Occurs → Hook Triggered → Logic Executes → Result Applied
```

---

# 4. EVENT SYSTEM

---

## 4.1 Supported Events

### Entity Events

| Event Name   | Description              |
| ------------ | ------------------------ |
| beforeCreate | Before record is created |
| afterCreate  | After record is created  |
| beforeUpdate | Before record is updated |
| afterUpdate  | After record is updated  |
| beforeDelete | Before record is deleted |
| afterDelete  | After record is deleted  |

---

## 4.2 System Events (Future)

* user.login
* role.assigned
* module.installed

---

# 5. HOOK TYPES

---

## 5.1 System Hooks (Code-Based)

* Defined by developers
* Used internally or by modules

---

## 5.2 Dynamic Hooks (Runtime)

* Defined via Admin UI
* Stored in database

# 6. DATA MODEL

---

## 6.1 `hooks` Collection

```ts
type HookRecord = {
  id: string;
  tenantId: string;

  name: string;
  entity: string; // e.g. "loan"
  event: string;  // e.g. "afterCreate"

  type: "function" | "workflow";

  config: HookConfig;

  enabled: boolean;

  createdAt: timestamp;
  updatedAt: timestamp;
};
```

---

## 6.2 Hook Configuration

```ts
type HookConfig = {
  script?: string; // sandboxed function
  actions?: HookAction[];
};
```

---

## 6.3 Action-Based Hooks (No-Code Friendly)

```ts
type HookAction =
  | { type: "updateField"; field: string; value: any }
  | { type: "createRecord"; entity: string; data: any }
  | { type: "sendNotification"; message: string }
  | { type: "callWebhook"; url: string };
```

---

# 7. EXECUTION ENGINE

---

## 7.1 Hook Execution Flow

```text
1. Event triggered
2. Fetch matching hooks
3. Filter enabled hooks
4. Execute sequentially or in parallel
5. Return results / apply mutations
```

---

## 7.2 Execution Context

Each hook receives:

```ts
type HookContext = {
  tenantId: string;

  entity: string;
  event: string;

  current: Record<string, any>; // new data
  previous?: Record<string, any>; // for updates

  user: AuthUser;

  services: {
    db: SafeDBClient;
    api: InternalAPI;
  };
};
```

---

# 8. SCRIPT EXECUTION (SANDBOX)

---

## 8.1 Security Requirements

* No direct Node.js access
* No filesystem access
* No external network access (unless explicitly allowed)
* Time-limited execution

---

## 8.2 Recommended Approach

Use sandbox:

* VM2 (Node.js)
* or isolated runtime service

---

## 8.3 Example Script

```ts
if (context.current.amount > 10000) {
  context.services.api.update("loan", context.current.id, {
    status: "REVIEW_REQUIRED"
  });
}
```

---

# 9. ACTION-BASED ENGINE (NO-CODE)

---

## 9.1 Purpose

Allow non-technical users to define logic.

---

## 9.2 Example

Trigger:

* afterCreate (loan)

Actions:

1. updateField → status = "Pending"
2. sendNotification → "Loan created"

---

## 9.3 Execution

* Interpreted sequentially
* No scripting required

---

# 10. INTEGRATION POINTS

---

## 10.1 Query Engine

* Hooks triggered during CRUD operations
* Must not break transactional integrity

---

## 10.2 Dynamic Entity Builder

* Hooks attach to dynamic entities
* Validate entity existence

---

## 10.3 Module System

* Modules can register hooks programmatically

---

## 10.4 RBAC

* Hook execution respects permissions
* Prevent unauthorized actions

---

# 11. ERROR HANDLING

---

## 11.1 Hook Failure Strategy

### before* hooks

* Fail → block operation

### after* hooks

* Fail → log error, do not block

---

## 11.2 Logging

Store:

```ts
type HookExecutionLog = {
  hookId: string;
  status: "success" | "error";
  error?: string;
  timestamp: number;
};
```

---

# 12. PERFORMANCE STRATEGY

---

## 12.1 Execution Mode

* before hooks → synchronous
* after hooks → async (queue-based optional)

---

## 12.2 Optimization

* Cache hooks per entity/event
* Batch execution where possible

# 16. ACCEPTANCE CRITERIA

System is complete when:

* Hooks trigger correctly for all CRUD events
* Admin can define hooks via UI
* Script execution is sandboxed and safe
* Action-based hooks work without code
* Errors are logged and handled properly

---

# 17. DESIGN CONSTRAINTS

* Must be secure (no arbitrary code execution)
* Must not degrade core system performance
* Must be tenant-isolated
* Must support dynamic entities
