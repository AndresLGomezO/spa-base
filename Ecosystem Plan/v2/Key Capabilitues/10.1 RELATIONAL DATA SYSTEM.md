# 10.1 RELATIONAL DATA SYSTEM — IMPLEMENTATION PLAN

---

# 1. PURPOSE

The Relational Data System enables **structured relationships between entities** in a schema-driven, multi-tenant environment.

It allows the platform to model real-world data such as:

* Users belonging to Organizations
* Orders linked to Customers
* Many-to-many relationships (e.g., Users ↔ Projects)

This system must:

* Integrate with existing entity definitions
* Remain Firestore-compatible (NoSQL constraints)
* Be queryable via the Query Engine (dependency)
* Avoid tight coupling between entities

---

# 2. GOALS

### Primary Goals

* Support **entity-to-entity relationships**
* Enable **forward and reverse lookups**
* Maintain **performance at scale**
* Keep system **schema-driven and extensible**

### Non-Goals

* No SQL-style joins
* No cross-tenant relationships
* No automatic deep graph resolution (handled by Query Engine)

---

# 3. SUPPORTED RELATION TYPES

## 3.1 One-to-One

Example:

* User → Profile

Stored as:

```ts
profileId: string
```

---

## 3.2 One-to-Many

Example:

* Organization → Users

Stored as:

* On child:

```ts
organizationId: string
```

Reverse lookup required.

---

## 3.3 Many-to-Many

Example:

* Users ↔ Projects

Stored as:

* Reference arrays OR join collection

Option A (simple):

```ts
projectIds: string[]
```

Option B (scalable):

```
user_projects collection
```

---

# 4. DATA MODEL DESIGN

## 4.1 Relation Field Definition

Extend `defineEntity`:

```ts
{
  name: "organizationId",
  type: "relation",
  relation: {
    target: "organization",
    type: "many-to-one", // relative to current entity
    required: true
  }
}
```

---

## 4.2 Relation Metadata Structure

```ts
type RelationConfig = {
  target: string;
  type: "one-to-one" | "one-to-many" | "many-to-one" | "many-to-many";
  inverse?: string; // optional reverse field
  required?: boolean;
  onDelete?: "restrict" | "cascade" | "nullify";
};
```

---

## 4.3 Storage Rules

| Relation Type | Storage Strategy         |
| ------------- | ------------------------ |
| One-to-One    | Store foreign key        |
| One-to-Many   | Store FK on "many" side  |
| Many-to-Many  | Array OR join collection |

---

## 4.4 Tenant Isolation

* All relations must reference entities within the **same tenant**
* Validation must enforce tenant consistency

---

# 5. SYSTEM COMPONENTS

---

## 5.1 Relation Resolver

### Responsibility

* Resolve references between entities

### Inputs

* Entity name
* Record(s)
* Relation config

### Outputs

* Hydrated records (optional)

---

## 5.2 Relation Validator

### Responsibility

* Validate referenced IDs exist
* Enforce tenant boundaries
* Enforce required constraints

### Runs during:

* Create
* Update

---

## 5.3 Reverse Lookup Handler

### Responsibility

* Enable querying "backwards"

Example:

* Get all Users for Organization

### Implementation

* Query Engine must support:

```ts
where("organizationId", "==", orgId)
```

---

## 5.4 Join Collection Handler (Many-to-Many)

### Responsibility

* Manage join tables

Example:

```
user_projects:
  - userId
  - projectId
```

### Required Features

* Insert/delete join records
* Query both directions

---

# 6. API BEHAVIOR

---

## 6.1 Create / Update

### Input Example

```json
{
  "name": "John",
  "organizationId": "org_123"
}
```

### Behavior

* Validate referenced entity exists
* Validate tenant match
* Store reference ID

---

## 6.2 Read

### Default Response

```json
{
  "id": "user_1",
  "organizationId": "org_123"
}
```

### Optional Expansion (future Query Engine)

```json
{
  "organization": {
    "id": "org_123",
    "name": "Acme"
  }
}
```

# 7. FIRESTORE CONSTRAINTS & STRATEGY

---

## 7.1 No Joins

All relationships must be resolved via:

* Multiple queries
* Denormalization when needed

---

## 7.2 Indexing

* Required for:

  * Reverse lookups
  * Array membership queries

---

## 7.3 Denormalization (Optional)

Example:

```ts
organizationName: string
```

Used for:

* Performance optimization
* Avoiding repeated lookups

# 11. ACCEPTANCE CRITERIA

System is complete when:

* Relations can be defined declaratively
* CRUD enforces relation validity
* Reverse lookups work reliably
* Many-to-many is supported
* Tenant isolation is enforced
* System performs under expected load

---

# 12. DESIGN CONSTRAINTS

* Must NOT break existing entity system
* Must NOT hardcode entity relationships
* Must remain schema-driven
* Must integrate cleanly with Query Engine
