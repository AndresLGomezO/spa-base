# 10.0 QUERY ENGINE — IMPLEMENTATION PLAN

---

# 1. PURPOSE

The Query Engine provides a **standardized, secure, and extensible way to retrieve data** across all entities.

It replaces ad-hoc querying with a **centralized abstraction layer** that:

* Enforces RBAC at query time
* Supports filtering, sorting, and pagination
* Enables relational lookups
* Ensures consistent performance patterns

This is **foundational infrastructure**, not a feature.

---

# 2. GOALS

### Primary Goals

* Unified querying interface for all entities
* Built-in RBAC enforcement
* Support for filtering, sorting, pagination
* Compatibility with Firestore constraints
* Extensible for future features (aggregations, relations, etc.)

### Non-Goals

* No SQL-like joins
* No arbitrary query execution
* No direct exposure of Firestore queries

---

# 3. CORE CONCEPT

All data access must go through:

```ts
queryEngine.find(entityName, queryConfig, context)
```

This becomes the **single entry point** for all reads in the system.

---

# 4. QUERY CONFIG STRUCTURE

## 4.1 Base Structure

```ts
type QueryConfig = {
  filter?: Filter[];
  sort?: Sort[];
  pagination?: {
    limit: number;
    cursor?: string;
  };
  select?: string[];
  include?: string[]; // relations (future)
};
```

---

## 4.2 Filters

```ts
type Filter = {
  field: string;
  operator: "==" | "!=" | ">" | "<" | ">=" | "<=" | "in" | "array-contains";
  value: any;
};
```

### Example

```ts
filter: [
  { field: "organizationId", operator: "==", value: "org_1" }
]
```

---

## 4.3 Sorting

```ts
type Sort = {
  field: string;
  direction: "asc" | "desc";
};
```

---

## 4.4 Pagination

Cursor-based:

```ts
pagination: {
  limit: 20,
  cursor: "lastDocId"
}
```

# 6. SYSTEM COMPONENTS

---

## 6.1 Query Parser

### Responsibility

* Validate query structure
* Normalize filters/sorts
* Reject invalid fields/operators

---

## 6.2 RBAC Filter Injector

### Responsibility

* Modify query to enforce permissions

### Example

If user can only see own records:

```ts
filter.push({
  field: "ownerId",
  operator: "==",
  value: context.userId
})
```

---

## 6.3 Tenant Enforcer

### Responsibility

* Automatically inject tenant filter

```ts
field: "tenantId" == context.tenantId
```

---

## 6.4 Firestore Query Builder

### Responsibility

* Convert QueryConfig → Firestore query

### Constraints

* One inequality field per query
* Composite indexes required

---

## 6.5 Result Formatter

### Responsibility

* Map Firestore docs → API response
* Apply `select`
* Attach cursor

---

## 6.6 Relation Resolver (Hook Point)

### Responsibility

* Expand relations if `include` is used (future)

---

# 7. QUERY EXECUTION FLOW

---

1. Receive query request
2. Validate QueryConfig
3. Inject tenant filter
4. Inject RBAC constraints
5. Validate fields against entity schema
6. Build Firestore query
7. Execute query
8. Format results
9. Return response

---

# 8. FIRESTORE CONSTRAINT HANDLING

---

## 8.1 Supported Operators

* `==`
* `<`, `<=`, `>`, `>=`
* `in`
* `array-contains`

---

## 8.2 Limitations

* No OR queries (initial version)
* Limited compound inequality support
* Requires indexes for complex queries

---

## 8.3 Strategy

* Fail fast on unsupported queries
* Provide clear error messages
* Log index requirements

---

# 9. SECURITY MODEL

---

## 9.1 Mandatory Enforcement

All queries must:

* Enforce tenant isolation
* Enforce RBAC constraints
* Validate fields against schema

---

## 9.2 Forbidden Actions

* Direct Firestore access outside Query Engine
* Bypassing RBAC filters
* Querying non-defined fields

# 13. ACCEPTANCE CRITERIA

System is complete when:

* All reads go through Query Engine
* RBAC is enforced at query level
* Tenant isolation is guaranteed
* Pagination works reliably
* Invalid queries are rejected
* Performance is stable

---

# 14. DESIGN CONSTRAINTS

* Must remain entity-schema driven
* Must NOT expose Firestore directly
* Must be extensible (relations, aggregations)
* Must not duplicate logic across services

---

# 16. SUMMARY

The Query Engine is the **data access backbone** of the platform.

It ensures:

* Security (RBAC + tenant)
* Consistency (single query interface)
* Scalability (controlled query patterns)
* Extensibility (foundation for all future features)

Without it, higher-level capabilities become fragile and inconsistent.

With it, the platform becomes **predictable, secure, and scalable by design**.
