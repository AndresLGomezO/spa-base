## 1. OVERVIEW & CONTEXT

In Phase 1 we achieved **tenant isolation** — each tenant’s data lives in its own Firestore path and is accessible only to members of that tenant. However, within a single tenant, all users who have `entity.read` permission could see **all records** of that entity. For a production SaaS, this is rarely sufficient. You need:

* **User‑level data ownership**: most records are created by / belong to a specific user.
* **Default scoping**: when a user queries the API, they see only their own records, unless they hold elevated privileges (e.g., `entity.read_all`) or the record has been explicitly shared.
* **Selective sharing**: the owner of a record can grant read or write access to another user inside the same tenant, and revoke it later.

This workstream extends the existing DAL, CRUD generator, and RBAC system to make user isolation the **default behavior**, while adding a clean sharing mechanism that does not break the existing security model.

---

## 2. OBJECTIVES

- **Automatic ownership**: Every new record automatically gets an `ownerId` field populated from the authenticated user’s ID.
- **Default query scoping**: All `findAll` / `findById` calls filter by `ownerId == currentUser`, **unless** the user has a special permission (like `entity.read_all`) or the record is shared.
- **Sharing API**: Provide dedicated, RBAC‑protected endpoints to share / unshare records with other users.
- **Consistent enforcement**: Both backend (API) and frontend (UI) respect the isolation rules. The frontend never shows actions or data the user shouldn’t see.
- **Audit trail**: All share/unshare operations are logged.

---

## 3. DESIGN PRINCIPLES

1. **Least privilege by default**: A user sees **nothing** unless they are the owner, have a share, or hold a higher‑level permission.
2. **Separation of concerns**: Ownership checks live in the Data Access Layer (DAL) and are invisible to the business logic above.
3. **Performance**: Queries remain Firestore‑friendly; we avoid complex client‑side filtering for large datasets.
4. **Flexibility**: The system allows per‑entity configuration — some entities might be “public” within the tenant (all users can read), others strictly private.
5. **Sharing is explicit**: No implicit sharing from “teams” or “groups” in the first iteration. (Groups can be added later via the RBAC role system if needed.)

## 4. TECHNICAL DESIGN

### 4.1 Data Model

#### 4.1.1 Ownership

Each entity document (e.g., `tenants/{tenantId}/{entityCollection}/{docId}`) will have an **`ownerId`** field of type `string`. This field is:

- **Required** on creation (set by the backend).
- **Immutable** after creation (an owner cannot be changed by users; only a tenant admin or superadmin could do so via a separate administrative operation).
- **Indexed** in Firestore to allow efficient queries like `WHERE ownerId == currentUser`.

**Example document (illustrative — `{entity}` is any registered entity):**
```json
{
  "id": "abc123",
  "name": "Acme Corp",
  "email": "contact@acme.com",
  "ownerId": "user_x",
  "createdAt": "2026-05-29T...",
  "updatedAt": "...",
  "...other fields..."
}
```

#### 4.1.2 Sharing

Sharing is stored in a **separate sub‑collection** per entity document, or as a top‑level array on the document. The sub‑collection approach is more scalable and avoids document size limits, but the array approach is simpler for small numbers of shares. We will start with an **array** for simplicity and migrate to a sub‑collection only if needed.

**Option A: Array on document (recommended start)**
```json
{
  ...
  "sharedWith": [
    { "userId": "user_y", "permission": "read" },
    { "userId": "user_z", "permission": "write" }
  ]
}
```
**Constraints:** The `sharedWith` array is always **owned and managed by the record owner** (and admins). It contains only `userId` strings that belong to the same tenant.

**Option B: Sub‑collection**  
`tenants/{tenantId}/{entityCollection}/{docId}/shares/{shareId}`  
Each share document: `{ userId, permission, createdAt }`  
*Future option if share volume grows.* Initial implementation uses **Option A (map on document)** for simplicity. Document the 100‑share limit; move to a sub‑collection only if needed later — **not** as a migration from production data (there is none).

### 4.2 Permission Model Additions

Current permissions: `entity.read`, `entity.create`, `entity.update`, `entity.delete`.

We will introduce **two new permission levels** per entity:

- `entity.read_all` – User can read **all** records of that entity within the tenant, bypassing ownership checks.
- `entity.write_all` – User can update/delete **any** record (implies `read_all`).

Standard `entity.read`, `entity.update`, `entity.delete` will now, by default, be **scoped to owned or shared records**. For example, `{entity}.read` means “can read `{entity}` records you own or that are shared with you”.

A user who has **only** `{entity}.read` will see:
- Records where `ownerId == currentUser`
- Records where `sharedWith` contains an entry with `userId == currentUser` and `permission == "read"` (or `"write"` which implies read).

Thus, the permission string alone does not grant full access; it’s the combination of permission and ownership/sharing that determines visibility.

**Note:** For entities that should be “tenant‑public” (all members can see all records), we will introduce an entity configuration flag `tenantWideRead: true`. When set, `entity.read` effectively acts as `read_all`. This is an easy opt‑out from user isolation.

### 4.3 DAL Modifications

The generic `BaseRepository<T>` currently operates on a collection path `tenants/{tenantId}/{entityName}`. We will enhance it to:

- **Create** – Automatically inject `ownerId` from the authenticated user context (passed as a method argument or via async hook). The `createdBy` and `updatedBy` fields will also be added for audit.
- **findAll(filters, context)** – Automatically add a `WHERE ownerId == context.userId` clause **unless** the context has the `read_all` permission for that entity. Additionally, for shared records, we need a compound query or a second query. In Firestore, we cannot do an OR query (owned OR shared) natively. We have two choices:
  1. **Denormalized “access list”** field: maintain an array `accessUsers` that contains `[ownerId, ...sharedUserIds]`. Then query `WHERE accessUsers CONTAINS currentUser`. This is efficient (single index scan) but requires updating `accessUsers` on every share change.
  2. **Two queries**: `WHERE ownerId == currentUser` and `WHERE sharedWith.userId == currentUser` (using a map or array membership query). Firestore supports `array-contains` on an array of strings. So if `sharedWith` is an array of `{userId, permission}` objects, we can’t directly query `array-contains` on a field inside objects. We’d need to store a separate array `sharedUserIds: ["user_y", "user_z"]` to enable `array-contains`. Then `findAll` would run two queries and merge results on the server (acceptable for small datasets, but not for large lists). We can also use a collection group index on a `shares` sub‑collection, but that’s complex.

**Recommended approach (simplicity + performance):**  
Use a **denormalized `accessUserIds` array** that combines owner + all shared users. The array is updated whenever sharing changes. The query becomes:
```ts
.where('accessUserIds', 'array-contains', currentUserId)
```
This works perfectly with Firestore and returns all records the user has any access to (owner or shared). To differentiate between owner and shared records later (for write permissions), the document still contains `ownerId` and `sharedWith` details. The `accessUserIds` is purely for query filtering.

- **findById(id, context)** – Fetch the document, then verify if `ownerId == context.userId` or `sharedWith` contains a matching share or if the user has `read_all`. If not, throw a **403 Forbidden** (or 404 to avoid information leakage).
- **update(id, data, context)** – Same ownership/share check, plus verify that if the user is only a shared collaborator, the share permission is `"write"`. Only the owner (or `write_all` user) can modify the `sharedWith` array.
- **delete(id, context)** – Only the owner or `delete_all` permission holder can delete.

### 4.4 Sharing API Endpoints

We will add two new endpoints **per entity**, automatically registered by the CRUD generator:

- **POST /api/tenant/:tenantId/entity/:entityName/:id/share**
  - Body: `{ userId: string, permission: "read" | "write" }`
  - RBAC: only the record owner or a user with `entity.manage_shares` (new permission) can call this.
  - Logic: adds the entry to `sharedWith`, updates `accessUserIds`, returns updated share list.
  
- **DELETE /api/tenant/:tenantId/entity/:entityName/:id/share/:userId**
  - RBAC: owner or `manage_shares`.
  - Logic: removes the user from `sharedWith`, updates `accessUserIds`.

- **GET /api/tenant/:tenantId/entity/:entityName/:id/share** (optional)
  - Returns list of shares (owner and admins only).

These endpoints must validate that the target `userId` belongs to the same tenant. A new helper service `TenantUserValidator` will verify existence.

### 4.5 UI Integration

- **EntityTable**: When fetching data, the backend already scopes results; the UI does not need to re‑filter. However, table action buttons (edit, delete) must be conditionally rendered based on the current user’s relationship to each record:
  - If `ownerId == currentUser` → show all actions.
  - Else if shared with `"write"` → show edit, not delete.
  - Else → only view.
- **EntityForm**: On create, `ownerId` is hidden. On edit, if the user is not the owner and only has write share, the form should disable owner‑only fields (like sharing controls) and maybe show a banner “You are editing a shared record”.
- **Sharing UI**:
  - Add a “Share” button on the detail view (or row actions) visible only to the record owner.
  - Opens a dialog to search for users in the tenant and select permission level.
  - List current shares with option to remove.
- **Permission‑aware routing**: No change needed, because routing is based on entity, not individual records.

### 4.6 Audit & Logging

All sharing operations (grant, revoke) must be logged to a dedicated Firestore collection `tenants/{tenantId}/_audit` with structure:
```json
{
  "action": "share_granted",
  "entity": "{entityName}",
  "recordId": "abc123",
  "actorId": "user_x",
  "targetUserId": "user_y",
  "permission": "read",
  "timestamp": "..."
}
```
This satisfies compliance requirements and aids troubleshooting.

## 5. IMPLEMENTATION STEPS

We will break the work into six sequential steps, each with a clear deliverable and validation.

### Step 1: System fields (greenfield — no migration)
**What:** Add `ownerId`, `accessUserIds`, `sharedWith` as **required system fields** in the entity layer and Zod full schema.  
**How:**
- Extend [`packages/entities/src/systemFields.ts`](../../../packages/entities/src/systemFields.ts) and schema builder so every entity document includes ownership/sharing fields.
- CRUD create handler injects `ownerId`, `createdBy`, `updatedBy`, `accessUserIds`, `sharedWith` from auth context — **never** from client input.
- No migration script, no optional fields for “old” records, no backfill.

**Validation:** New records always persist complete ownership fields. Unit tests validate schema; integration tests create fresh records only.

### Step 2: Repository auto‑population & default scoping
**What:** Update `BaseRepository` to:
- On `create`, set `ownerId`, `createdBy`, `updatedBy` from the request context, and initialize `accessUserIds = [ownerId]`, `sharedWith = []`.
- On `findAll`, add `.where('accessUserIds', 'array-contains', context.userId)` **unless** the user has `read_all` permission (in which case no filter is applied).
- On `findById`, `update`, `delete`, perform the ownership/share check.

**Permission check helpers:**
- Create a `canAccessRecord(record, userPermissions, userId)` function that returns `{ canRead, canWrite, canDelete, isOwner }`.
- Integrate with RBAC: the middleware already resolves user permissions; we pass them to the repository methods.

**Validation:** Create two users: A and B. A creates a record. B cannot see it via API (get list or by ID). A can see it. B gets 403 on direct ID access.

### Step 3: Elevation Permissions & Tenant‑Public Entities
**What:** Add `entity.read_all`, `entity.write_all`, `entity.delete_all` permissions to the RBAC config and middleware. Update repository logic to bypass ownership when these are present.
Also add entity metadata flag `tenantWideRead: true` that makes `entity.read` equivalent to `read_all` (useful for entities like “Projects” where all members need visibility).

**Implementation:**
- In the entity definition config stored in Firestore, add a boolean `tenantWideRead`.
- When building permissions on login, if `tenantWideRead == true`, treat `entity.read` as the “all” variant in the permission set. Alternatively, the DAL can just skip the `accessUserIds` filter when that flag is true.

**Validation:** Assign `{entity}.read_all` to a role. A user with that role sees all records of that entity, even without ownership/share. Flag `tenantWideRead: true` on an entity makes regular `read` users see all records.

### Step 4: Sharing Subsystem (Backend)
**What:** Implement the sharing endpoints described in 4.4, and the array management logic.

**Implementation details:**
- When a share is added, push `{ userId, permission }` into `sharedWith` array, and add `userId` to `accessUserIds` (if not already present). Use `FieldValue.arrayUnion` for atomic updates.
- When a share is removed, use `arrayRemove`.
- Ensure the sharing endpoints check that the target user is a member of the same tenant (validate via a lookup to `tenants/{tenantId}/users` collection).
- Write audit logs.
- Ensure only the owner (or `manage_shares` privilege) can modify sharing; verify `ownerId == context.userId` in the endpoint.

**Validation:**
- Owner shares a record with user C (read). C can now see the record in list and detail.
- Owner shares with write. C can edit but not delete.
- Owner revokes share. C can no longer access the record.

### Step 5: Frontend Updates
**What:** Update all generated entity pages to respect ownership and sharing.

**Tasks:**
- In the table component, add a `permissions` check per row: if row is not owned, hide delete button; if shared with read‑only, hide edit button.
- In detail/edit form, disable fields based on write permissions; show a share button for owners.
- Build the **ShareDialog** component:
  - Search users (with debounce) via a new endpoint `GET /api/tenant/:tenantId/users?search=...` (to be added).
  - Display current shares.
  - Allow add/remove.
- Use React context for `currentUserId` (from auth).

**Validation:**
- UI matches permissions: viewer sees no edit/delete; shared editor can edit but not delete or share.
- Sharing dialog works seamlessly.

### Step 6: Audit Log Integration & Edge Case Handling
**What:** Ensure all data access violations are logged, and edge cases (e.g., user leaves tenant, record ownership transfer) are gracefully handled.

**Edge cases:**
- **User removed from tenant**: Their shares should be automatically cleaned up (or orphaned shares remain harmless because the user’s ID is no longer valid; the sharing check will still work but the user can’t log in). We can implement a cleanup job triggered by user deletion.
- **Owner transferred**: An admin may reassign `ownerId` (via admin API). This must update `accessUserIds` to remove old owner and add new owner. We’ll provide an admin endpoint `PATCH /api/.../transfer-ownership` that does this atomically.
- **Concurrent share updates**: Firestore’s `arrayUnion`/`arrayRemove` are safe for concurrent modifications, but the `sharedWith` array of objects cannot be manipulated atomically with object updates. We may need to use a **transaction** when updating `sharedWith` and `accessUserIds` together to avoid inconsistency. Alternatively, we could store `sharedWith` as a map: `{ [userId]: permission }` and keep `accessUserIds` as an array; then we can update the map field directly. Map fields allow granular updates without transactions. This is a better design. We’ll use a map: `sharedWith: { user_y: "read", user_z: "write" }`. `accessUserIds` is still an array for querying. When updating sharing, we modify both the map and the array inside a Firestore transaction or batched write.

**Validation:** Edge case unit tests pass, audit logs appear in `_audit`.

## 6. SECURITY CONSIDERATIONS

- **No information leakage**: When a user requests a record they cannot access, return a generic `404 Not Found` instead of `403 Forbidden` (to avoid revealing existence).
- **Validation of target user**: Always verify that the user being shared with is part of the current tenant and not a cross‑tenant ID.
- **Input sanitization**: `userId` in share endpoints must match the Firestore user document ID format.
- **Authorization on share endpoints**: Strictly check `ownerId` or `manage_shares` permission.
- **Rate limiting**: Sharing endpoints could be abused; apply per‑user rate limits.
- **Audit logs immutable**: Use Firestore security rules to prevent modification of `_audit` documents by non‑admin users.

---

## 7. PERFORMANCE IMPLICATIONS

- **`accessUserIds` array‑contains query**: Requires a composite index on `accessUserIds` and any other sorted/filtered field (e.g., `createdAt`). The index size grows with the number of shares per record, but typically small.
- **Two‑query approach avoided**: By using denormalized `accessUserIds`, we stick to a single query, keeping Firestore costs low.
- **Caching**: User permissions and tenant metadata are already cached; no additional caching needed for ownership data itself because it’s directly queried.
- **Bulk operations**: If a record is shared with thousands of users, the document size may become an issue. We’ll document a limit of 100 shares per record initially. If exceeded, we’ll move to a sub‑collection model for sharing. This is flagged for future monitoring.

## 8. VALIDATION CRITERIA (END‑TO‑END)

The workstream is successful when:

1. **Default isolation**: Two users in the same tenant, with only basic `entity.read`, cannot see each other’s records.
2. **Explicit sharing**: Owner shares a record → sharee sees it; revoke → sharee loses access immediately.
3. **Write sharing**: Sharee with `write` can update but not delete or share further.
4. **Elevated permissions**: A user with `entity.read_all` sees all records; `entity.write_all` can edit any record.
5. **Tenant‑public entity**: Setting `tenantWideRead: true` allows all tenant members to see all records without sharing.
6. **UI consistency**: Buttons and forms reflect the exact access rights.
7. **Audit trail**: Every share grant/revoke is logged.
8. **Performance**: No noticeable latency increase for list queries when user has hundreds of owned records.

## 9. POTENTIAL PITFALLS & MITIGATIONS

| Pitfall | Mitigation |
|--------|------------|
| Large `sharedWith` arrays causing document size bloat | Limit shares to 100; monitor; design for future sub‑collection |
| Firestore `array-contains` can’t query on object array fields | Use map for `sharedWith` and separate `accessUserIds` array |
| Concurrent share updates causing inconsistency | Use Firestore transactions for updating both map and array |
| Users accidentally removed from tenant leaving orphaned shares | Implement a cleanup script triggered by user removal |
| Performance of list queries when a user has many shared records | `accessUserIds` query is a single index scan; acceptable |
| Frontend showing edit buttons to viewers due to stale state | Derive row‑level permissions from the `ownerId` and `sharedWith` returned in the API response; no client‑side guesswork |
