## 🧩 WORKSTREAM 3: ADVANCED QUERY ENGINE — DETAILED PLAN

---

## 1. OVERVIEW & CONTEXT

The Phase 1 CRUD generator provides basic list endpoints with **pagination** (`limit` / `cursor`), but no **filtering**, **sorting**, or **search** capabilities. Every list request returns all records the user is allowed to see, in natural Firestore order, which is rarely sufficient for real‑world usage.

Workstream 3 adds a **unified query engine** that exposes:

- **Filtering** by field values with standard operators (`eq`, `neq`, `gt`, `gte`, `lt`, `lte`, `in`, `contains`, `startsWith`, `endsWith`).
- **Sorting** by one or more fields, ascending/descending.
- **Full‑text search** across string fields (basic, using Firestore’s native string comparison tricks + optional future integration with a search service).
- **Cursor‑based pagination** (already partially implemented) extended to work correctly with filtered and sorted results.

All queries respect the **ownership isolation** from Workstream 1 and **RBAC** from Phase 1. The query engine is the **only** code path that builds Firestore queries for entity data — DAL repositories delegate to it.

Because the app is not yet in production, we design this as a **clean, generic layer** that sits on top of Firestore but abstracts its limitations enough to be swapped later. No data migrations, no legacy handling. All examples (filtering orders by total, searching customer names) are illustrative — no concrete test entities will be committed.

---

## 2. OBJECTIVES

- **Declarative query API**: A simple, URL‑based query language using query parameters.
- **Filtering**: Support common operators on all non‑sensitive fields. The engine automatically rejects filters on encrypted fields.
- **Sorting**: Single and multi‑field sort, respecting Firestore’s composite index requirements. Sorting on encrypted fields is forbidden.
- **Search**: Basic free‑text search across all string fields of an entity (configurable), implemented efficiently within Firestore’s limitations (client‑side post‑filter or `>=`/`<=` pattern). A documented path to plug in a dedicated search service (Algolia, Typesense) in the future.
- **Pagination**: Cursor‑based pagination (stable, scalable) that works across filtered/sorted result sets.
- **Ownership scoping**: All queries automatically include the `accessUserIds` filter from Workstream 1 — no escape hatch.
- **Performance**: Query execution is as close to Firestore’s native capabilities as possible, with a clear fallback to server‑side post‑filtering when Firestore cannot satisfy the combination of filters natively.
- **Developer tooling**: Auto‑generation of necessary composite indexes for common filter/sort combinations (or a clear guide).
- **UI integration**: `<EntityTable>` gains sortable columns, a filter row, and a search bar, all driven by the entity’s field metadata.

---

## 3. DESIGN PRINCIPLES

1. **Ownership‑first**: Every query, no matter the filters or sorts, always starts with the ownership scope. The `accessUserIds` constraint is non‑optional and cannot be overridden by any query parameter.
2. **Schema‑driven**: The engine knows the entity’s field types, which ones are encrypted (`sensitive: true`), and which are sortable/filterable. Invalid requests are rejected early with clear error messages.
3. **Firestore‑aware, not Firestore‑bound**: The query engine exposes a generic `QuerySpec` interface and translates it to Firestore queries. If we later move to PostgreSQL, only the translator changes.
4. **Fail safe, not fail open**: If a requested filter/sort combination cannot be executed efficiently in Firestore, the engine **refuses the request** and instructs the client how to adjust (e.g., which index to create) — it never silently degrades to a full table scan (except for tiny datasets where we can allow with a flag, but not by default).
5. **Pagination stability**: Cursor‑based pagination prevents duplicate/missed records when data is being added concurrently. Offset‑based pagination is not supported (Firestore doesn’t support it natively anyway).
6. **Clear error messages**: The API returns structured error codes like `INVALID_FILTER_FIELD`, `UNSUPPORTED_OPERATOR`, `COMPOSITE_INDEX_REQUIRED`, with human‑readable messages and a link to documentation.

## 4. TECHNICAL DESIGN

### 4.1 Query API Contract

All list endpoints accept the following new query parameters:

| Parameter | Example | Description |
|-----------|---------|-------------|
| `filter` | `filter[name]=Acme&filter[age][gte]=18` | Filters in bracket notation. Multiple filters are ANDed. |
| `sort` | `sort=name,-createdAt` | Comma‑separated field names. Prefix `-` for descending. |
| `search` | `search=john` | Full‑text search term (runs against configured searchable string fields). |
| `limit` | `limit=25` | Page size (default 25, max 100). |
| `cursor` | `cursor=abc123` | Opaque pagination cursor (returned in previous response under `nextCursor`). |

**Full example:**
```
GET /api/entity/customer?filter[status]=active&filter[createdAt][gte]=2025-01-01&sort=-createdAt&search=smith&limit=10&cursor=xxx
```

**Response envelope (updated):**
```json
{
  "success": true,
  "data": [ ... ],
  "meta": {
    "nextCursor": "abc124",
    "hasMore": true,
    "totalCount": null   // Not supported in Firestore without extra cost; omitted or computed on demand
  }
}
```

**Filter operators:** `eq` (default), `neq`, `gt`, `gte`, `lt`, `lte`, `in` (comma‑separated values), `contains`, `startsWith`, `endsWith`.

**Field types and allowed operators:**

| Field type | Allowed operators |
|------------|------------------|
| `string` | `eq`, `neq`, `in`, `contains`, `startsWith`, `endsWith` |
| `number` | `eq`, `neq`, `gt`, `gte`, `lt`, `lte`, `in` |
| `boolean` | `eq`, `neq` |
| `date` | `eq`, `neq`, `gt`, `gte`, `lt`, `lte` |
| `reference` | `eq`, `neq`, `in` (acts on the foreign key string) |
| `sensitive` | **No filter or sort allowed** — returns `QUERY_ON_ENCRYPTED_FIELD` error. |
| `array` | (future) |

### 4.2 Firestore Query Builder

**File (new):** `packages/query-engine/src/firestore-query-builder.ts`

The query builder takes:
- Entity metadata (field definitions, tenant ID, collection path)
- User context (userId, permissions, tenantId)
- Parsed query spec (filters, sort, search, limit, cursor)

It produces a sequence of Firestore `Query` objects (or an error). The builder follows this process:

1. **Ownership scope**: Always the first filter: `WHERE accessUserIds ARRAY-CONTAINS currentUserId`. If the entity has `tenantWideRead: true`, this filter is omitted (as per Workstream 1).
2. **Search pre‑filter**: If `search` is provided, the builder selects the first index‑compatible string field (or uses a dedicated `_searchTokens` array) and applies a range filter to simulate prefix match (`>= term`, `< term + '\uf8ff'`). Multi‑field search is handled by combining `_searchTokens` from all searchable fields, or we restrict to a single designated `searchableFields` configuration on the entity. (Detailed design in 4.5.)
3. **Apply sort orders**: The `ORDER BY` clauses are added. Firestore requires the first sort field to be the same field used for an inequality filter (`WHERE field > ...`), if any. The builder must verify and reject if not aligned.
4. **Apply equality filters**: All `eq` and `in` filters are added as `WHERE` clauses. Firestore supports `IN` queries (up to 30 values) and `ARRAY-CONTAINS-ANY` for array membership. Multiple equality filters on different fields are ANDed and supported.
5. **Apply inequality/range filters**: At most **one** field can have inequality filters (`>`, `<`, `>=`, `<=`) per query. If multiple range fields are requested, the builder must either:
   - Pick the one that matches the sort order (if a sort on that field exists) and reject others with `UNSUPPORTED_FILTER_COMBINATION`, suggesting client‑side filtering, OR
   - Fall back to server‑side post‑filtering if the dataset is small enough (configurable threshold). For v1, we choose the strict approach: **reject** if multiple range filters on different fields are requested, with a clear error and hint to create a composite index if one range and sort can be aligned.
6. **Client‑side post‑filter for unsupported operators**: `contains`, `startsWith`, `endsWith` on string fields cannot be natively performed by Firestore (except via the range trick for prefix). After Firestore returns the results, a server‑side filter removes non‑matching documents. This is acceptable for moderate result sets.
7. **Cursor**: The cursor is a base64‑encoded token containing the last document’s snapshot fields relevant to the sort order. The builder decodes it and applies `startAfter` or `startAt` accordingly.

**Result:** The query builder returns an object with:
- `firestoreQuery`: the `Query` object (or array of queries if `IN` is used).
- `postFilters`: array of predicate functions to apply after fetch (for unsupported operators, or for `search` fine‑matching).
- `warnings`: array of strings (e.g., “partial index usage, some filters applied client‑side”).

### 4.3 Filtering Details

**Parsing:** `filter[field]=value` (operator defaults to `eq`). `filter[field][gte]=value`. Multiple filters on the same field? Only allowed for range operators (gte+lte). The parser flattens them.

**Validation:** The entity schema provides the field list. Unknown fields → `INVALID_FILTER_FIELD`. Sensitive fields → `QUERY_ON_ENCRYPTED_FIELD`. Unsupported operator for field type → `UNSUPPORTED_OPERATOR`.

**`in` operator:** Accepts comma‑separated values (`filter[status]=active,inactive`) — translated to Firestore `IN` query (max 30 values). Values are parsed and validated against field type.

**`contains` operator:** Not natively supported. Implemented as a post‑filter after fetching candidate records (maybe using a prefix range on the field to narrow down candidates). If `contains` is used alone without other filters, it may be expensive; we’ll add a configuration `allowUnindexedQueries` per entity (default false). If `false`, requesting `contains` without a sufficiently narrowing pre‑filter returns `QUERY_TOO_BROAD`.

### 4.4 Sorting

**Syntax:** `sort=name,-createdAt` → order by `name` ascending, then `createdAt` descending.

**Constraints:**
- Sorting on encrypted fields is forbidden.
- Firestore requires a composite index for each combination of equality filters + sort fields. The engine will **not** attempt to perform client‑side sorting for large datasets. If the required index doesn’t exist, Firestore will throw an error, which we catch and return as `COMPOSITE_INDEX_REQUIRED` with a link to the Firebase console or auto‑generated index creation link.

**Default sort:** If no `sort` parameter is provided, the entity definition can specify a `defaultSort` (e.g., `-createdAt`). If none, Firestore returns documents in natural order (by ID), which is not useful; we’ll enforce a default `-createdAt` unless overridden.

### 4.5 Full‑Text Search

Firestore does not support native full‑text search. For v1, we implement a **prefix‑based search** using string range queries and a **search token** array.

**Design:**
- The entity can declare `searchableFields: string[]` (fields of type `string`).
- When a record is created/updated, a system field `_searchTokens` (not exposed to users) is populated with lowercase, tokenized versions of the values of those fields. For example, "Acme Corp" → `["acme", "corp"]`. This allows `array-contains` queries. But `array-contains` only supports exact match, not prefix. For prefix, we can generate substrings: `["a", "ac", "acm", "acme", "c", "co", "cor", "corp"]`. This explodes storage but enables instant prefix search with `array-contains`. Too costly. Alternative: we use Firestore’s string range trick on a single `searchField` composite: store searchable text in a field `_searchString` (lowercased) and query `WHERE _searchString >= term AND _searchString < term + 'z'`. This only works for prefix search, not infix. This is acceptable for a basic "starts with" search.

**Recommended approach (v1):**
- The `search` query parameter triggers a prefix search on the entity’s first `searchableField` or a designated `searchField`. If no field is designated, search returns an error `SEARCH_NOT_CONFIGURED`.
- The query builder constructs a range filter on that field: `WHERE searchField >= searchTerm AND searchField < searchTerm + '\uf8ff'`. This is an inequality filter, so it must align with the sort order: if the user provides a `sort` on another field, it’s incompatible. The engine can:
  - Enforce that when `search` is used, sorting is limited to the search field itself, OR
  - Use a separate composite index where the search field is the first sort field, then apply the range filter and sort on searchField, and then post‑sort on other fields if needed (but that means sorting on a different field requires client‑side sorting of the entire result set, which is bad). For v1, we restrict: when `search` is active, sorting is forced to the search field (ascending relevance = alphabetical order). This is a known limitation; we document it.

**Future path:** Integration with Algolia/Typesense via a module. The query engine will emit a hook so that a search service module can intercept the `search` parameter and return results, bypassing Firestore.

### 4.6 Pagination

We already have cursor‑based pagination in Phase 1 (via `startAfter` with a document snapshot). We’ll extend it to work correctly with filtered and sorted queries.

**Cursor token:** The API returns `nextCursor` in the meta. The token encodes:
- The last document’s field values corresponding to the sort fields (to maintain correct position even if sort fields have duplicate values).
- A version identifier to detect schema changes (optional).

**Implementation:** The token is base64‑encoded JSON, signed with a server secret to prevent tampering and client‑side cursor forging (which could be used to enumerate documents). The query builder decodes, verifies signature, extracts the document reference (or sort field values) and calls `startAfter(docSnapshot)`.

**Edge cases:**
- If the last document is deleted between requests, the cursor becomes invalid. The API returns an error `INVALID_CURSOR` and the client should restart from the first page.
- Changing filters/sort resets the cursor (cursor is context‑dependent). The frontend will handle this by clearing the cursor when search/filter/sort changes.

### 4.7 Integration with Ownership & RBAC

The query engine will be the **single place** where list queries are built. It replaces any ad‑hoc query building in DAL/repositories.

- The `OwnershipQueryInjector` from Workstream 1 is now an **integral part** of the query builder, not a separate middleware. The builder always prepends the ownership filter.
- RBAC is still checked at the route level: the user must have `{entity}.read` permission to reach the list endpoint. The query engine assumes that check has passed.
- Field‑level permissions are not implemented yet (that’s Workstream 4), but the engine is designed to later accept a list of allowed fields and strip non‑readable fields from the response.

### 4.8 Frontend Integration

The `EntityTable` component will be significantly upgraded:

- **Column headers**: Click to sort ascending/descending. Display a sort indicator. The table passes `?sort=...` to the API.
- **Filter row**: Beneath the headers, an optional filter row where each column shows an appropriate input (text for string, number for number, date picker for date, boolean checkbox). Entering a value adds the filter to the API call.
- **Search bar**: A global search input above the table triggers the `?search=` parameter.
- **Pagination controls**: “Previous” / “Next” buttons using the `nextCursor` and a history stack of cursors (since Firestore doesn’t support backwards pagination natively, we’ll implement forward‑only pagination with a back button that remembers previous cursors).
- All these state changes update the URL search params, making the table state bookmarkable and sharable.

Store previous cursors; on "previous", pop the last cursor and pass the previous one as the cursor? ## 6. SECURITY CONSIDERATIONS

| Concern | Mitigation |
|---------|------------|
| Filter injection / NoSQL injection | All values are parsed and validated against the entity’s Zod schema before building queries. String values are used as literals, not interpreted. |
| Accessing other users' data via filters | Ownership scope (`accessUserIds`) is always the first filter, unbypassable. Filters only reduce the result set; they cannot expand it. |
| Sensitive field exposure through filter errors | Error messages for `QUERY_ON_ENCRYPTED_FIELD` simply state "Filtering on encrypted fields is not supported." No field values revealed. |
| Cursor tampering | Cursor token is signed with HMAC; server validates signature before decoding. Tampered cursors return `INVALID_CURSOR`. |
| Denial of service via expensive queries | Rate limiting per user (already planned). Also, `contains`/`search` operators without index support are rejected if `allowUnindexedQueries` is false (default). Limit max page size to 100. |
| Data enumeration via cursor | The cursor is opaque; no sequence of IDs is exposed. |

## 7. PERFORMANCE CHARACTERISTICS

- **Equality filters & IN queries**: Firestore native, fast. `IN` supports up to 30 values.
- **Single range filter + sort**: Fast with a composite index (`field1 ASC, field2 DESC`). Index auto‑created via error link.
- **Multiple range filters**: Rejected to prevent full scan.
- **`contains` / `startsWith` / `endsWith`**: Post‑filtered on results from a prefix range query. If the pre‑filter yields a large set (e.g., `contains` on a common word), performance may degrade. We’ll monitor and add `allowUnindexedQueries` config.
- **Search**: Prefix range query scans an index on the search field; similar to range filter performance. Only one search field supported per request; no cross‑field search in v1.
- **Pagination**: Cursor‑based, no offset overhead. Each page fetches at most `limit` documents.
- **Ownership filter**: `array-contains` query is indexed; performance depends on number of users in `accessUserIds`. Typically small.

## 8. VALIDATION CRITERIA

1. `GET /api/entity/customer?filter[status]=active` returns only records with `status=active` that the user owns.
2. `filter[age][gte]=18&filter[age][lte]=65` works as a range on the same field.
3. `filter[status]=active&filter[age][gte]=18` on different fields (equality + range) works if the composite index exists; otherwise returns helpful error.
4. `filter[name][contains]=john` returns records where name includes "john" (case‑insensitive) among owned records.
5. `sort=-createdAt` orders by newest first; secondary sort `sort=status,-createdAt` orders by status then newest.
6. `search=Acme` with a designated searchable string field returns owned records starting with "Acme".
7. Filtering or sorting on a field marked `sensitive: true` returns `QUERY_ON_ENCRYPTED_FIELD`.
8. Pagination: `nextCursor` works across pages of filtered/sorted data; invalid cursor returns `INVALID_CURSOR`.
9. Ownership isolation is intact: user A cannot see user B's records via any filter/search combination.
10. Frontend table reflects sort indicators, filter inputs, search bar, and pagination buttons.

## 9. POTENTIAL PITFALLS & MITIGATIONS

| Pitfall | Mitigation |
|--------|------------|
| Firestore limitation: only one inequality filter per query | Reject multi‑range queries with clear error; suggest client‑side filtering for secondary range |
| `contains` on large datasets causes slow post‑filtering | Gate behind `allowUnindexedQueries: false` by default; require explicit opt‑in or use a predefined subset (e.g., filter by date range first) |
| Search conflicts with custom sort | When `search` is active, override sort to the search field; document limitation |
| Composite indexes not created leading to runtime errors | Catch and surface `COMPOSITE_INDEX_REQUIRED` with creation link; provide tooling to auto‑generate index files |
| Sensitive fields appearing in filter error messages | No raw field values in errors; generic message |
| Frontend filter state not synced with URL | Use URL search params as the single source of truth for table state; bookmarkable |
| Backward pagination complexity | Implement cursor stack on frontend; accept limitations of eventual consistency |
