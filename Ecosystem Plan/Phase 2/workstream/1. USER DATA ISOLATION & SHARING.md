### WORKSTREAM 1: USER DATA ISOLATION & SHARING — IMPLEMENTATION REFERENCE

---

## 1. OVERVIEW & CONTEXT

In Phase 1 we achieved **tenant isolation** — each tenant's data lives in its own Firestore path (`tenants/{tenantId}/{collection}/{docId}`) and is accessible only to members of that tenant. Workstream 1 extends this to **user-level isolation**: within a tenant, each user sees only their own records unless an explicit share exists.

**Key design decision:** No role — including superadmin or tenant-admin — can bypass ownership. The only exceptions are:

- The record has been **explicitly shared** with the user (read or write).
- The entity is flagged **`tenantWideRead: true`**, which skips the ownership filter for reads only.

There are no `read_all`, `write_all`, or `delete_all` elevation permissions. This was an intentional simplification to enforce strict data ownership.

---

## 2. OBJECTIVES (AS IMPLEMENTED)

- **Automatic ownership**: Every new record gets an `ownerId` field set to the authenticated user's UID on create.
- **Default query scoping**: All list/detail queries filter by `accessUserIds array-contains currentUser`, ensuring users only see owned or shared records.
- **Sharing API**: Dedicated endpoints to grant, revoke, and list shares — gated by the `{entity}.share` permission and restricted to the record owner.
- **No re-sharing**: A user who receives a shared record (read or write) cannot re-share it. Only the original owner can share.
- **Consistent enforcement**: Backend (API) and frontend (UI) both respect isolation. The frontend never shows actions the user cannot perform.
- **Audit trail**: All share/unshare operations are logged to `tenants/{tenantId}/_audit`.
- **Hybrid field-level encryption**: Fields marked `sensitive` are encrypted at rest using AES-256-GCM with per-tenant derived keys.

---

## 3. DESIGN PRINCIPLES

1. **Least privilege by default**: A user sees nothing unless they are the owner or have an explicit share.
2. **Role-agnostic enforcement**: No role (superadmin, tenant-admin) bypasses ownership. This is enforced at both query level (`OwnershipQueryInjector`) and record level (`checkRecordAccess`).
3. **Performance**: A single denormalized `accessUserIds` array enables efficient `array-contains` queries in Firestore — no multi-query merging required.
4. **Flexibility**: Per-entity `tenantWideRead` flag allows opting out of isolation for shared-visibility entities.
5. **Sharing is explicit and owner-only**: No implicit sharing via teams, groups, or roles.

---

## 4. TECHNICAL DESIGN (AS IMPLEMENTED)

### 4.1 Data Model

#### System Fields

Every entity document includes these system fields (defined in `packages/entities/src/systemFields.ts` and `packages/entities/src/schema/buildEntitySchemas.ts`):

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `id` | `string` | Yes | Document ID |
| `tenantId` | `string` | Yes | Owning tenant |
| `createdAt` | `string` (ISO datetime) | Yes | Creation timestamp |
| `updatedAt` | `string` (ISO datetime) | Yes | Last update timestamp |
| `ownerId` | `string` | Optional | UID of the creating user |
| `accessUserIds` | `string[]` | Optional | Denormalized array for query filtering: `[ownerId, ...sharedUserIds]` |
| `sharedWith` | `Record<string, string>` | Optional | Map of `{ userId: permission }` where permission is `"read"` or `"write"` |

**Example Document:**
```json
{
  "id": "abc123",
  "tenantId": "tenant_1",
  "ownerId": "user_x",
  "accessUserIds": ["user_x", "user_y"],
  "sharedWith": { "user_y": "read" },
  "createdAt": "2026-05-29T...",
  "updatedAt": "...",
  "name": "Acme Corp",
  "_schemaVersion": 1
}
```

**Why a map for `sharedWith`:** Maps allow granular field-level updates (`sharedWith.user_y = "read"`) without reading/rewriting the entire object. Combined with `FieldValue.arrayUnion`/`arrayRemove` on `accessUserIds`, sharing updates are performed atomically inside a Firestore transaction.

### 4.2 Permission Model

Permissions generated per entity by `buildPermissions()` in `packages/entities/src/metadata/buildPermissions.ts`:

| Permission | Purpose |
|------------|---------|
| `{entity}.read` | Can read owned/shared records |
| `{entity}.create` | Can create new records |
| `{entity}.update` | Can update owned records or records shared with `write` |
| `{entity}.delete` | Can delete owned records only |
| `{entity}.share` | Can share/unshare owned records with other users |
| `{entity}.manage_shares` | Reserved for future admin share management |

**What was NOT implemented (by design):**
- `read_all`, `write_all`, `delete_all` — deliberately excluded to enforce strict ownership. Even superadmin cannot view other users' data.

**Entity-level configuration:**
- `tenantWideRead: boolean` — When `true` on an entity definition, the `OwnershipQueryInjector` skips the `accessUserIds` filter for list queries, making all records visible to all tenant members with `{entity}.read`.

### 4.3 Query-Level Enforcement

**File:** `apps/api/src/access/ownership-query-injector.ts`

The `OwnershipQueryInjector` implements the `RbacQueryInjector` interface and is invoked by the query engine before every list query. It injects:

```ts
{ field: "accessUserIds", operator: "array-contains", value: currentUserId }
```

This filter is **skipped only** when the entity has `tenantWideRead: true`. No role or permission bypasses it otherwise.

### 4.4 Record-Level Enforcement

**File:** `apps/api/src/access/record-access.ts`

The `checkRecordAccess(record, userId)` function determines per-record access:

```ts
{
  canRead:  isOwner || sharePermission !== null,
  canWrite: isOwner || sharePermission === "write",
  canDelete: isOwner,  // only owner can delete
  isOwner,
  sharePermission: "read" | "write" | null,
}
```

This function takes **no role or permission arguments** — it operates purely on `ownerId` and `sharedWith` fields. It is called in the CRUD routes for GET-by-ID, PUT, and DELETE operations.

### 4.5 Sharing Service

**File:** `apps/api/src/access/share-service.ts`

The `ShareService` provides three operations:

- **`grantShare`** — Adds `{ [targetUserId]: permission }` to the `sharedWith` map and `targetUserId` to `accessUserIds` via a Firestore transaction.
- **`revokeShare`** — Removes the user from both `sharedWith` and `accessUserIds`.
- **`listShares`** — Returns current shares for a record.

**Access control:** The `assertShareAccess` function enforces **owner-only** access — only the record owner (`data.ownerId === callerUserId`) can perform share operations. No role bypasses this.

### 4.6 Share API Routes

**File:** `apps/api/src/access/register-share-routes.ts`

Three routes are registered for all entities:

| Method | Path | Description |
|--------|------|-------------|
| `POST` | `/api/:entityName/:id/share` | Grant share (`{ userId, permission }`) |
| `DELETE` | `/api/:entityName/:id/share/:userId` | Revoke share |
| `GET` | `/api/:entityName/:id/share` | List shares |

All three routes enforce:
1. **`{entity}.share` permission** — checked via `hasPermission()` before reaching the service. Returns 403 if the role doesn't include this permission.
2. **Owner-only** — the share service verifies the caller is the record owner.

Result: a user must have **both** the `{entity}.share` role permission **and** be the record owner to share/unshare.

### 4.7 Hybrid Field-Level Encryption

**Packages:** `packages/encryption`, `apps/api/src/crud/sensitive-fields.ts`

Fields marked `sensitive: true` in the entity definition are encrypted at rest using:

- **Algorithm:** AES-256-GCM
- **Key derivation:** HKDF-SHA256 from a master key (`TENANT_ENCRYPTION_MASTER_KEY` env var) using the `tenantId` as salt, producing a unique 256-bit key per tenant.
- **Storage format:** `iv.ciphertext.authTag` (base64-encoded)

Encryption/decryption is handled transparently in the Firestore converter layer (`packages/firestore-converters/src/entity/create-entity-converter.ts`):
- **Write path:** Data passes schema validation first, then sensitive fields are encrypted before Firestore write.
- **Read path:** Encrypted fields are decrypted before schema validation and domain object construction.

This ensures encrypted values never interfere with Zod schema validation.

### 4.8 CRUD Route Integration

**File:** `apps/api/src/crud/register-crud-routes.ts`

On **POST (create)**:
1. User fields are validated against `createSchema`.
2. System fields are injected: `id`, `tenantId`, `createdAt`, `updatedAt`, `ownerId` (from `request.ctx.uid`), `accessUserIds: [ownerId]`, `sharedWith: {}`.
3. Full record is validated against `schema`.
4. Relation hooks run.
5. Record is persisted via `activeRepository.create()` (encryption happens in the converter).

On **GET (list)**:
- The query engine applies the `OwnershipQueryInjector` filter automatically.

On **GET (by ID)**, **PUT**, **DELETE**:
- `checkRecordAccess()` verifies the caller's relationship to the record.
- Edit requires ownership or `write` share.
- Delete requires ownership.

### 4.9 UI Integration

**`EntityTable` (`apps/web/app/components/entity/EntityTable.tsx`):**
- Row-level action buttons are derived from the record's `ownerId` and `sharedWith`:
  - **Edit:** shown if owner or shared with `write`.
  - **Delete:** shown only for owner.
  - **Share:** shown only if `permissions.canShare && item.ownerId === currentUserId` (owner-only, no re-sharing).
- Share button displays a badge with the count of shared users.
- Sensitive fields display a lock icon in column headers.

**`useEntityPermissions` (`apps/web/app/hooks/useEntityPermissions.ts`):**
- Returns: `canRead`, `canCreate`, `canUpdate`, `canDelete`, `canShare`, `canManageShares`.
- `canShare` checks the `{entity}.share` permission.

**Entity Definition UI:**
- `tenantWideRead` toggle available in both the entity creation wizard and editor form.
- `sensitive` checkbox available per field (disabled for relation fields).

### 4.10 Audit & Logging

All sharing operations are logged to `tenants/{tenantId}/_audit` via the `AuditLogger`:

```json
{
  "action": "share_granted | share_revoked",
  "entity": "entityName",
  "recordId": "abc123",
  "actorId": "user_x",
  "targetUserId": "user_y",
  "permission": "read",
  "timestamp": "2026-05-31T..."
}
```

## 6. SECURITY MODEL SUMMARY

- **No role bypasses ownership.** Not superadmin, not tenant-admin. This is enforced at both query and record level.
- **Owner-only sharing.** Only `ownerId === callerUserId` can grant/revoke shares. No re-sharing by shared users.
- **Permission-gated sharing.** The `{entity}.share` role permission must be granted for the share button and API to work.
- **Sensitive field encryption.** AES-256-GCM with per-tenant derived keys. Encrypted in the converter layer (after schema validation, before Firestore write).
- **Audit trail.** Every share grant/revoke is immutably logged.

---

## 7. PERFORMANCE CHARACTERISTICS

- **Single-query scoping:** The `accessUserIds array-contains` filter uses a single Firestore index scan. No multi-query merging.
- **Atomic share updates:** Firestore transactions ensure `sharedWith` map and `accessUserIds` array stay consistent.
- **Encryption overhead:** Minimal — only fields marked `sensitive` are encrypted. Key derivation is cached per tenant within the converter lifecycle.
- **Document size:** `sharedWith` map + `accessUserIds` array grow with shares. Practical limit ~100 shares per record before considering sub-collection migration.

---

## 8. VALIDATION CRITERIA

1. **Default isolation**: Two users in the same tenant with `{entity}.read` cannot see each other's records.
2. **Explicit sharing**: Owner shares a record -> sharee sees it; revoke -> sharee loses access immediately.
3. **Write sharing**: Sharee with `write` can update but not delete or share further.
4. **No role bypass**: Superadmin and tenant-admin cannot view other users' data unless explicitly shared.
5. **Tenant-wide read**: Setting `tenantWideRead: true` on an entity allows all tenant members to see all records.
6. **Share permission gating**: A role without `{entity}.share` cannot use the share button or API.
7. **UI consistency**: Buttons and forms reflect exact access rights per row.
8. **Audit trail**: Every share grant/revoke is logged.
9. **Encryption**: Sensitive fields are encrypted at rest and decrypted transparently on read.

---

## 9. POTENTIAL PITFALLS & MITIGATIONS

| Pitfall | Mitigation |
|--------|------------|
| Large `sharedWith` maps causing document size bloat | Limit shares to ~100 per record; monitor; design for future sub-collection |
| Concurrent share updates causing inconsistency | All share mutations run inside Firestore transactions |
| Users removed from tenant leaving orphaned shares | Shares become harmless (user can't authenticate); cleanup job can be added later |
| Encrypted fields breaking schema validation | Encryption runs in the converter layer, after domain schema validation on write and before deserialization on read |
| Sensitive fields queried/sorted | Query engine rejects filter/sort on `sensitive` fields with `QUERY_VALIDATION_ERROR` |
| Frontend showing share button to non-owners | `canShareRow` requires both `permissions.canShare` and `item.ownerId === currentUserId` |
