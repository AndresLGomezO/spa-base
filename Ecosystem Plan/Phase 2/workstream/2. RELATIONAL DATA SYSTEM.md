The key architectural constraints are now clear:

- **No role bypasses ownership** — not even superadmin
- **No `read_all` / `write_all` / `delete_all` elevation permissions**
- **Only exceptions**: explicit sharing or `tenantWideRead: true`
- **Owner‑only sharing**, gated by both `{entity}.share` permission and ownership
- **Hybrid field‑level encryption** for sensitive fields

## 🧩 WORKSTREAM 2: RELATIONAL DATA SYSTEM — ALIGNED PLAN

---

## 1. OVERVIEW & CONTEXT

Workstream 1 established strict user‑level data isolation: every record has an `ownerId`, queries are scoped by `accessUserIds`, and no role — not even superadmin — can bypass ownership. The only paths to see another user's record are an **explicit share** or an entity flagged **`tenantWideRead: true`**.

Workstream 2 introduces **relationships between entities** while fully respecting this isolation model. An order can reference a customer, but only if the user creating the order can **already see** that customer (via ownership, share, or tenant‑wide read). When the API populates a reference, it must never leak a record the current user cannot access.

Because the app is **not yet in production**, we design this as a brand‑new capability integrated directly with the current codebase — no migrations, no legacy handling. All entity examples (customer, order, etc.) are illustrative; **no concrete entities will be added to the repository**.

---

## 2. OBJECTIVES

- **Declarative reference fields**: Entity definitions can include fields of type `reference` pointing to another entity.
- **One‑to‑many and many‑to‑many support**: Via foreign keys and junction entities. (One‑to‑one is a future constraint on top of many‑to‑one.)
- **Ownership‑respecting validation**: When setting a reference, the target record must be accessible to the current user (owned, shared, or tenant‑wide readable).
- **Safe population**: The API can expand referenced records (`?populate=customer`), but only returns records the user can access. Inaccessible references return `null`.
- **Reverse navigation**: Virtual reverse fields (e.g., `customer.orders`) that query the child collection through the same ownership scope.
- **Referential integrity**: Configurable `onDelete` policies (`restrict`, `cascade`, `set-null`) that respect ownership — a user cannot cascade‑delete records they don't own.
- **UI components**: Autocomplete selectors for references, inline display in tables, clickable links in detail views, and reverse‑relation lists.

---

## 3. DESIGN PRINCIPLES

1. **No ownership bypass through relationships**: A reference is a pointer. Setting it, seeing it, or following it must all pass through the same `checkRecordAccess` / `OwnershipQueryInjector` gates from Workstream 1.
2. **Schema‑driven, not code‑driven**: Relationship configuration lives in entity metadata. The CRUD generator, API, and UI interpret it generically.
3. **Firestore‑friendly storage**: Foreign keys stored as simple string fields. No embedded sub‑documents. No unbounded arrays on the parent side of one‑to‑many.
4. **Efficient population**: For list endpoints, referenced records are batch‑fetched via `getAll` after collecting distinct foreign keys.
5. **Security by construction**: The reference validator and populator both use the existing `checkRecordAccess` function. There is no separate permission path.
6. **Start with many‑to‑one, expand later**: Many‑to‑one (foreign key on child) and its reverse (virtual one‑to‑many) are the foundation. Many‑to‑many uses an explicit junction entity — no hidden magic.

---

## 4. TECHNICAL DESIGN

### 4.1 Reference Field Definition

A new field type `reference` is added to the entity field schema:

```ts
// Inside an entity's fields array
{
  name: "customer",
  type: "reference",
  entity: "customer",             // target entity name
  relationship: "many-to-one",    // "many-to-one" | "one-to-one" (future)
  reverseField: "orders",         // optional: virtual field name on the target entity
  onDelete: "restrict",           // "restrict" | "cascade" | "set-null"
  displayField: "name"            // optional: field on target to show in UI; defaults to target's displayField
}
```

**Supported in v1:** `many-to-one` references with optional `reverseField`.  
**Supported via junction entity:** `many-to-many` (two `many-to-one` references on a user‑defined link entity).  
**Deferred:** `one-to-one` (adds a uniqueness constraint on the foreign key — can be layered on later).

### 4.2 Storage Model

#### 4.2.1 Many‑to‑One (Foreign Key)

The referencing document stores a simple string field:

```
orders/{orderId}: {
  customerId: "abc123",   // references customers/{customerId}
  ...
}
```

`customerId` is validated as a non‑empty string by Zod. The reference validator (see 4.4) ensures the target exists and is accessible.

#### 4.2.2 One‑to‑Many (Reverse / Virtual)

No data stored on the parent. The reverse field (`customer.orders`) is a **virtual computed field**. When populated, it executes a query on the child collection filtered by the foreign key, passing through the `OwnershipQueryInjector`.

#### 4.2.3 Many‑to‑Many (Junction Entity)

The developer defines a normal entity with two reference fields:

```ts
defineEntity({
  name: "task_tags",
  fields: {
    taskId: { type: "reference", entity: "task" },
    tagId:  { type: "reference", entity: "tag" },
  }
})
```

The platform treats `task_tags` as a standard CRUD entity. Population and permission checks work identically. To get all tags for a task, the client calls:

```
GET /api/entity/task_tags?filter[taskId]=task1&populate=tag
```

No special many‑to‑many endpoints are needed; the existing query + populate infrastructure handles it.

### 4.3 Reference Validation (Ownership‑Respecting)

**File (new):** `apps/api/src/access/reference-validator.ts`

When a record is created or updated, every reference field is validated through `ReferenceValidator`:

1. **Existence check** (optional, configurable per entity or per field): Fetches the target document to confirm it exists.
2. **Access check** (always enforced): Calls `checkRecordAccess(targetRecord, currentUserId)` from Workstream 1. If `canRead` is `false`, the operation is rejected with:
   - HTTP `400` + error code `REFERENCE_ACCESS_DENIED`
   - Message: `"You do not have access to the referenced {entity} record '{id}'."`

**Exception:** If the target entity has `tenantWideRead: true`, the access check automatically passes for any tenant member with `{entity}.read` — consistent with Workstream 1's query‑level behavior.

**Important:** The reference validator uses the **same `checkRecordAccess` function** that guards direct CRUD. There is no separate code path, no admin override. If the user can't read the target via GET /entity/:id, they can't reference it either.

### 4.4 Population Engine (Ownership‑Safe)

**File (new):** `apps/api/src/access/reference-populator.ts`

The `ReferencePopulator` handles `?populate=fieldName` on GET requests.

**For a single record:**
1. Read the foreign key value (e.g., `customerId`).
2. Fetch the target document through the standard DAL `findById` (which calls `checkRecordAccess` internally).
3. If access is denied, set the populated field to `null` and add a warning to `X-Population-Warnings` header.

**For a list:**
1. Collect all distinct foreign key values from the result set.
2. Batch‑fetch all referenced documents via `getAll` (or individual `findById` calls that go through access checks).
3. Merge into the response. Records the user cannot access become `null`.

**Why `null` instead of omitting or erroring:** Returning `null` prevents information leakage. The foreign key ID itself is visible (it's part of the record the user owns or was shared), but the populated data is withheld. The alternative — returning a `403` — would reveal that a record with that ID exists, which is a side‑channel leak.

**Population depth limit:** Only one level of population is supported in v1. `?populate=customer.contacts` is not allowed. This prevents accidental expensive queries and infinite loops on cyclic references.

### 4.5 On‑Delete Policies (Ownership‑Bound)

When a record is deleted, the system checks the reverse index for all entities that reference it.

**Reverse index (built from entity registry):**
```
{
  "customer": [
    { sourceEntity: "order", fieldName: "customerId", onDelete: "restrict" },
    { sourceEntity: "note",  fieldName: "customerId", onDelete: "cascade" },
  ]
}
```

**Policy behaviors:**

| Policy | Behavior | Ownership Constraint |
|--------|----------|---------------------|
| `restrict` | If any referencing records exist, the delete is blocked with error `REFERENCED_RECORDS_EXIST` | Only checks records the **current user owns**. If another user references this record, the owner can still delete it — the other user's reference becomes a dangling pointer (acceptable for v1; we'll log a warning). |
| `cascade` | All referencing records are deleted along with the parent | **Only deletes records owned by the current user.** Records owned by others are left as dangling references. The response includes a `danglingReferences` array warning the user. |
| `set-null` | The foreign key is set to `null` on all referencing records | **Only updates records owned by the current user.** Others are left untouched. |

**Why ownership‑bound cascades:** In Workstream 1's model, no user can delete another user's record. Cascade must not become a backdoor to violate this. If User A deletes a customer, User B's orders referencing that customer are not silently deleted. They become dangling references, which the UI can display as "Deleted Customer".

**Future improvement:** A background job could notify affected users or offer to reassign references, but this is out of scope for v1.

### 4.6 API Endpoint Enhancements

The CRUD generator (`apps/api/src/crud/register-crud-routes.ts`) is extended:

- **`populate` query parameter** parsed and passed to `ReferencePopulator`.
- **Reverse population**: When an entity has `reverseField` defined on one of its incoming references, `?populate=orders` triggers a child collection query filtered by the parent ID, routed through the `OwnershipQueryInjector`.
- **Delete route**: Before executing delete, the reverse index is consulted, and the appropriate `onDelete` policy is enforced.

**Error response structure:**
```json
{
  "success": false,
  "error": {
    "code": "REFERENCE_ACCESS_DENIED",
    "message": "You do not have access to the referenced customer record 'abc123'.",
    "details": {
      "field": "customerId",
      "targetEntity": "customer",
      "targetId": "abc123"
    }
  }
}
```

### 4.7 Frontend Components

#### 4.7.1 Reference Autocomplete (`ReferenceField`)

A new form component for fields of type `reference`:

- **Data source**: Calls the target entity's list endpoint with `?search=` parameter, passing through the user's ownership scope automatically (the API already applies `OwnershipQueryInjector`).
- **Display**: Uses the target entity's `displayField` (or the reference field's `displayField` override) to show options.
- **Selected state**: Shows a chip or pill with the display value and a link to the target's detail page.
- **Permission awareness**: If the user lacks `{targetEntity}.read`, the dropdown is disabled and shows "Insufficient permissions". If the user has read but the target entity is not `tenantWideRead`, they'll only see their own records — which is correct.

#### 4.7.2 Table Column Rendering

In `EntityTable`, columns for reference fields automatically:
- Request `?populate=fieldName` in the list API call.
- Render the display value of the populated record (if accessible) or show the raw ID in muted text with a "Not accessible" tooltip.

#### 4.7.3 Detail View Links

On an entity detail page, reference fields render as clickable links:
```tsx
<Link to={`/app/${tenantId}/entity/${targetEntity}/${foreignKey}`}>
  {populatedValue?.displayField ?? foreignKey}
</Link>
```

If the populated record is `null` (inaccessible), the link is still rendered (the ID is visible), but clicking it may lead to a 404/403 — consistent with direct navigation behavior.

#### 4.7.4 Reverse Relation Lists (`RelatedRecords`)

For entities with `reverseField` definitions, the detail page can include a `<RelatedRecords>` component:

- Queries the child entity's list endpoint with `?filter[foreignKey]=parentId`.
- Displays a mini‑table with the same permission‑scoped row actions as `EntityTable`.
- Respects the user's ownership — they'll only see child records they own or were shared.

## 6. SECURITY CONSIDERATIONS

| Concern | Mitigation |
|---------|------------|
| Reference as ownership bypass | `ReferenceValidator` uses `checkRecordAccess` — same gate as direct access |
| Population leaking inaccessible records | Returns `null`, not error; foreign key ID is already visible to the record owner |
| Cascade delete as backdoor to delete others' records | Cascade only affects records where `ownerId == currentUserId` |
| Enumeration via reference attempts | Returning `REFERENCE_ACCESS_DENIED` reveals existence — acceptable because the user already has access to the referencing record and would see the ID anyway |
| Cyclic population causing infinite loops | Population depth limited to 1 level in v1 |
| Large batch population DoS | Distinct foreign keys capped at 100 per request; `400` if exceeded |

---

## 7. PERFORMANCE CHARACTERISTICS

- **Existence check on write**: One extra `get` per reference field. Configurable opt‑out per field.
- **Population on single record**: One extra `get` per populated field.
- **Population on list**: `getAll` batch for distinct foreign keys (e.g., 100 orders referencing 5 customers = 5 extra reads).
- **Reverse population**: One additional query on child collection, filtered and ownership‑scoped.
- **Cascade delete**: Transactional for ≤50 referencing records; larger cascades deferred to a background queue (future).
- **Reverse index**: Built in memory from the entity registry at startup; negligible overhead.

## 8. VALIDATION CRITERIA

1. An entity can define a `reference` field pointing to another entity.
2. Creating/updating a record with a reference to an **inaccessible** target fails with `REFERENCE_ACCESS_DENIED`.
3. Creating/updating a record with a reference to an **accessible** target succeeds.
4. `?populate=customer` on a list endpoint returns full referenced objects for accessible records, `null` for inaccessible ones.
5. Reverse population (`?populate=orders`) returns only child records the current user can access.
6. `onDelete: restrict` blocks deletion if owned referencing records exist.
7. `onDelete: cascade` deletes owned referencing records but leaves others as dangling references.
8. Reference autocomplete shows only records the user can access.
9. Table columns for references display the target's `displayField`, not the raw ID.
10. Detail view renders reference fields as clickable links.
11. All behaviors hold regardless of the user's role — no admin bypass.
